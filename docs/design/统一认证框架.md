# 统一认证框架

## 概述

本文档描述了 SSO 项目的统一认证框架设计。框架采用**两层抽象**，清晰区分两个不同层面的问题：

1. **身份认证层（Authentication Layer）** —— 解决"如何证明用户身份"的问题
   - 密码、邮箱验证码、短信验证码、微信、钉钉、LDAP 等
2. **协议接入层（Protocol Layer）** —— 解决"应用如何对接 SSO"的问题
   - OIDC/OAuth2、SAML、CAS、自定义 API 等

**关键关系：** 协议接入层在需要验证用户身份时，调用身份认证层完成认证。每种协议可以使用任意一种或多种认证方式。

## 核心概念对比

### 身份认证方式 vs 协议接入方式

| 维度 | 身份认证方式 | 协议接入方式 |
|------|------------|------------|
| **解决的问题** | 如何证明"你是谁" | 应用如何对接 SSO |
| **典型示例** | 密码、邮箱验证码、短信验证码、微信、钉钉、LDAP | OIDC、SAML、CAS、自定义 API |
| **在架构中的位置** | 身份认证层（底层） | 协议接入层（上层） |
| **输出产物** | AuthenticationResult (userId, claims) | Code / Assertion / Ticket / Token |
| **是否面向终端用户** | ✅ 是（用户直接交互） | ❌ 否（面向应用开发者） |
| **可否组合使用** | ✅ 用户登录时可选择任意方式 | ❌ 一个应用通常只对接一种协议 |

### 身份认证方式一览

| 认证方式 | 凭证类型 | 是否需要浏览器 | 是否经过 Pipeline | 典型场景 |
|---------|---------|--------------|-----------------|---------|
| **密码** | Username + Password | 可选 | ✅ 是 | 表单登录、Password Grant |
| **短信验证码** | Phone + Code | 可选 | ✅ 是 | 移动端快捷登录 |
| **邮件验证码** | Email + Code | 可选 | ✅ 是 | 无密码登录 |
| **OAuth2 社交** | Provider + ResolvedUser | ✅ 是 | ✅ 是 | 钉钉、企业微信 |
| **LDAP/AD** | Username + Password + Domain | 可选 | ✅ 是 | 企业 AD 域登录 |

### OAuth2/OIDC 协议模式一览

| 模式 | 是否需要用户 | 安全性 | 认证方式 | 典型场景 |
|------|------------|--------|---------|---------|
| **授权码模式** (+ PKCE) | ✅ 是 | ⭐⭐⭐⭐⭐ | 登录阶段使用任意认证方式 | Web 应用、移动应用、SPA |
| **密码模式** | ✅ 是 | ⭐⭐ | 密码认证 | 遗留系统迁移、受信任客户端 |
| **客户端凭证** | ❌ 否 | ⭐⭐⭐⭐ | 不经过认证层（无用户） | 微服务间认证 |
| **SSO 主动推送** | ✅ 是 | ⭐⭐⭐⭐ | 依赖已有会话 | 门户推送、应用间跳转 |

> 💡 **提示：** 刷新令牌（Refresh Token）不是独立的授权模式，而是 OAuth2 流程的通用机制，用于在 Access Token 过期后获取新的 Token，无需用户重新登录。

> ⚠️ **注意：**
> - OAuth2 的授权模式**不是**认证方式。授权码模式在用户登录阶段，可以调用密码、验证码、钉钉等任意认证方式。
> - PKCE 是授权码模式的**增强机制**（防止授权码劫持），不是独立的授权模式。公共客户端（SPA、移动端）必须使用授权码 + PKCE。
> - 密码模式安全性较低，仅限受信任客户端使用，不推荐作为新应用的首选方案。

## 身份认证层实现

### 1. AuthenticationStrategy (认证策略接口)

```java
public interface AuthenticationStrategy {
    AuthenticationMethod getMethod();
    boolean supports(AuthenticationCredentials credentials);
    AuthenticationResult authenticate(AuthenticationCredentials credentials);
    default boolean isRedirectBased() { return false; }
}
```

**职责：**
- 定义统一的认证接口
- 每种认证方式实现此接口
- 负责凭证验证和用户解析

### 2. AuthenticationCredentials (认证凭证)

使用 Java Sealed Interface 定义支持的凭证类型：

```java
public sealed interface AuthenticationCredentials {
    record PasswordCredentials(String username, String password) 
        implements AuthenticationCredentials {}
    record SmsCodeCredentials(String phone, String code) 
        implements AuthenticationCredentials {}
    record EmailCodeCredentials(String email, String code) 
        implements AuthenticationCredentials {}
    record OAuth2Credentials(String provider, User resolvedUser) 
        implements AuthenticationCredentials {}
    record LdapCredentials(String username, String password, String domain) 
        implements AuthenticationCredentials {}
    // Future: MfaCredentials, BiometricCredentials, etc.
}
```

### 3. AuthenticationDispatcher (认证分发器)

```java
@Component
public class AuthenticationDispatcher {
    private final List<AuthenticationStrategy> strategies;
    
    public AuthenticationResult authenticate(AuthenticationCredentials credentials) {
        return strategies.stream()
            .filter(s -> s.supports(credentials))
            .findFirst()
            .orElseThrow(...)
            .authenticate(credentials);
    }
}
```

**职责：**
- 根据凭证类型路由到相应的策略
- 支持策略的动态注册和发现
- 统一的认证入口点

### 4. PreAuthenticationPipeline (前处理管道)

责任链模式处理认证前的安全检查，**在任何策略执行之前**运行：

1. **RateLimitHandler** - 频率限制，防暴力破解（基于 IP + 用户名滑动窗口计数）
2. **AccountLockoutHandler** - 账号锁定状态检查（连续 N 次失败后临时锁定）
3. **CredentialValidationHandler** - 凭证格式校验（邮箱格式、手机号格式等）
4. **IpWhitelistHandler** - IP 白名单 / 黑名单检查

> **注意：** 前处理管道中的安全检查是**轻量级**的（通常读 Redis 缓存），不涉及数据库查询。账户状态验证等**重量级**检查放在后处理管道中。

### 5. PostAuthenticationPipeline (后处理管道)

> **⚠️ 已重构为事件驱动架构 (2026-05-22, 更新于 2026-05-23)**
>
> 原来的后处理管道（PostAuthenticationPipeline + PostAuthHandler）已重构为基于 Spring 事件驱动的架构：
> - `AuthenticationCompletedEvent` - 认证完成事件（含 ResultHolder 用于结果回传）
> - `AuthenticationFailedEvent` - 认证失败事件（触发失败审计）
> - `AccountStatusValidationListener` (Order=1) - 验证账户状态
> - `TenantResolutionAndSecurityContextListener` (Order=2) - 租户解析+权限加载+安全上下文建立（通过 ResultHolder 回传 AuthenticationResult）
> - `LoginRecordListener` (Order=3) - 记录登录时间戳（@Transactional）
> - `AuditEventListener` (Order=4) - 发布审计事件到 RocketMQ（使用 ObjectProvider 弱依赖）
>
> **关键设计：**
> - ResultHolder 模式：Spring 事件发布默认同步执行，`TenantResolutionAndSecurityContextListener` 将计算结果写入事件内嵌的 `ResultHolder`，`completeAuthentication()` 在发布返回后读取，传递给 `ProtocolRouter` 做路由决策。
> - RocketMQ 弱依赖：`AuditEventListener` 通过 `ObjectProvider<RocketMQTemplate>` 注入，RocketMQ 不可用时降级为本地日志，不阻塞启动。
> - 认证失败审计：`UnifiedAuthenticationFailureHandler` 发布 `AuthenticationFailedEvent`，`AuditEventListener` 监听并记录 LOGIN_FAILURE。
>
> **架构优势：**
> - 完全解耦：Post-authentication 逻辑通过事件驱动，零循环依赖
> - 开闭原则：新增监听器无需修改任何现有代码
> - 可测试性强：每个监听器可独立单元测试
> - 天然支持异步：未来可直接添加 `@Async` 实现异步处理
> - 优雅降级：中间件不可用时不影响核心认证流程
>
> 详细内容请参阅本章节「循环依赖重构」部分。

责任链模式处理认证成功后的通用逻辑：

1. **AccountStatusValidationHandler** - 验证账户状态（数据库查询，确认未被禁用）
2. **TenantResolutionHandler** - 解析租户上下文
3. **LoginRecordHandler** - 记录登录信息
4. **PermissionLoadingHandler** - 加载权限
5. **SecurityContextEstablishmentHandler** - 建立安全上下文
6. **AuditEventHandler** - 发布审计事件

> **注意：** 以上 Handler 已重构为事件监听器（EventListener），通过 `AuthenticationCompletedEvent` 事件触发。

## 循环依赖重构 (2026-05-22)

### 重构背景

在 iam-auth-server 模块中，存在多个循环依赖问题，需要启用 `allow-circular-references: true` 才能正常启动。这违反了 Spring 的最佳实践，并可能导致未来的兼容性问题。

### 重构方案

采用**事件驱动 + ObjectProvider** 的技术最理想方案，彻底解决循环依赖问题。

### 核心改动

#### 1. 引入事件驱动架构

**新增文件 (6个)**:

| 文件路径 | 作用 | 替代的原Handler |
|---------|------|----------------|
| `event/AuthenticationCompletedEvent.java` | 认证完成事件（含 ResultHolder 回传机制） | - |
| `event/AuthenticationFailedEvent.java` | 认证失败事件（触发失败审计） | - |
| `listener/LoginRecordListener.java` | 记录登录时间戳 | LoginRecordHandler |
| `listener/AuditEventListener.java` | 发布审计事件到 RocketMQ（成功+失败） | AuditEventHandler |
| `listener/AccountStatusValidationListener.java` | 验证账户状态 | AccountStatusValidationHandler |
| `listener/TenantResolutionAndSecurityContextListener.java` | 租户解析+权限加载+安全上下文建立 | TenantResolutionHandler + PermissionLoadingHandler + SecurityContextEstablishmentHandler (合并3个) |

**架构优势**:
- ✅ 完全解耦：Post-authentication 逻辑通过事件驱动，零循环依赖
- ✅ 开闭原则：新增监听器无需修改任何现有代码
- ✅ 可测试性强：每个监听器可独立单元测试
- ✅ 天然支持异步：未来可直接添加 `@Async` 实现异步处理

#### 2. 使用 ObjectProvider 延迟注入

**修改文件 (3个)**:

| 文件 | 修改内容 | 解决的循环链 |
|------|---------|-------------|
| `PreAuthenticationPipeline.java` | `List<PreAuthHandler>` → `ObjectProvider<List<PreAuthHandler>>` | Pipeline → Handler → Service → Pipeline |
| `CompositeAuthenticationProvider.java` | `List<AuthenticationStrategy>` → `ObjectProvider<List<AuthenticationStrategy>>` | Provider → Strategy → Repository → Provider |
| `DefaultSecurityConfig.java` | 直接注入 → `ObjectProvider<AuthenticationApplicationService>` + `ObjectProvider<ProtocolRouter>` | SecurityConfig → ApplicationService → Pipeline → SecurityConfig |

**技术原理**:
```java
// 重构前（构造时循环）
private final List<PreAuthHandler> handlers;

// 重构后（延迟解析）
private final ObjectProvider<List<PreAuthHandler>> handlersProvider;

// 使用时才解析
List<PreAuthHandler> handlers = handlersProvider.getIfAvailable(List::of);
```

#### 3. 重构 AuthenticationApplicationService

**修改文件**: `AuthenticationApplicationService.java`

**关键改动**:
```java
// 重构前：同步调用 Pipeline
public AuthenticationResult completeAuthentication(User user, AuthenticationMethod method, 
        HttpServletRequest request) {
    return pipeline.execute(user, method, request);
}

// 重构后：发布事件
public AuthenticationResult completeAuthentication(User user, AuthenticationMethod method, 
        HttpServletRequest request) {
    eventPublisher.publishEvent(
            AuthenticationCompletedEvent.of(this, user, method, request));
    return AuthenticationResult.basic(user, method);
}
```

**新增方法**: `AuthenticationResult.basic()` - 创建基础认证结果

#### 4. 移除循环依赖配置

**修改文件**: `application.yml`

```yaml
# 已删除
spring:
  main:
    allow-circular-references: true  # ❌ 已移除
```

### 循环依赖解决效果

#### 重构前（❌ 存在循环依赖）

```

  → AuthenticationApplicationService 
  → PostAuthenticationPipeline 
  → List<PostAuthHandler> (Spring自动注入所有实现)
  → PermissionLoadingHandler 
  → TenantAccountRoleApplicationService

```

**依赖图**: 存在环（Cycle）

```
  → 发布 AuthenticationCompletedEvent ✅

```

### 架构设计

租户上下文（TenantContext）采用 ThreadLocal 存储，在整个请求生命周期中提供用户和租户信息。

**核心组件：**

1. **TenantContext** (iam-common)
   - 位置：`iam.platform.common.context.TenantContext`
   - 存储内容：userId, userName, tenantId, tenantAccountId
   - 标准 HTTP Headers：
     - `X-User-Id`: 用户 ID
     - `X-User-Name`: 用户名
     - `X-Tenant-Id`: 租户 ID
     - `X-Tenant-Account-Id`: 租户账户 ID
     - `X-User-Roles`: 用户角色（逗号分隔）
     - `X-User-Permissions`: 用户权限（逗号分隔）

2. **GatewayHeaderContextFilter** (iam-common)
   - 位置：`iam.platform.common.context.GatewayHeaderContextFilter`
   - 职责：从网关 Header 中提取租户上下文并填充到 TenantContext
   - 特性：容错处理，Number FormatException 不会导致请求失败

3. **各服务的 Filter 注册：**
   - **iam-admin-server**: `AdminGatewayHeaderFilter` 注册 GatewayHeaderContextFilter
   - **iam-auth-server**: `TenantAwareAuthenticationFilter` 从网关 Header 提取租户上下文
   - **iam-bff-server**: `BffGatewayHeaderFilter` 注册 GatewayHeaderContextFilter
   - **iam-gateway**: `JwtClaimsHeaderFilter` 从 JWT Claims 提取并设置 Header

### 租户上下文传递流程

**场景 1：通过网关访问（所有浏览器和 API 调用）**
```
客户端 → Gateway (JwtClaimsHeaderFilter 提取 JWT Claims)
         ↓ 设置 X-User-*, X-Tenant-* Headers
     下游服务 (GatewayHeaderContextFilter/TenantAwareAuthenticationFilter 从 Header 填充 TenantContext)
         ↓
     业务逻辑使用 TenantContext.getCurrentTenantId() 等
```

**架构原则：**
- ✅ 所有浏览器访问都经过网关（包括认证服务）
- ✅ 租户上下文统一通过 JWT → 网关请求头 → TenantContext 传递
- ✅ 下游服务仅从网关请求头提取租户上下文
- ✅ Session 仅用于 OAuth2 SavedRequest 和 CAS SLO，不用于业务逻辑

### 关键实现细节

1. **网关请求头提取** (TenantAwareAuthenticationFilter)
   ```java
   // 仅从网关 Header 恢复租户上下文
   String userId = request.getHeader(TenantContext.HEADER_USER_ID);
   if (userId != null && !userId.isEmpty()) {
       TenantContext.populateFromHeaders(request);
       log.debug("Tenant context populated from gateway headers: userId={}", userId);
   }
   
   // ✅ 已移除: restoreTenantContextFromSession(request)
   // ✅ Session 仅用于 OAuth2 SavedRequest 和 CAS SLO
   ```

2. **容错处理** (TenantContext.populateFromHeaders)
   ```java
   // Long 解析失败时跳过，不中断请求
   try {
       setCurrentUserId(Long.parseLong(userId.trim()));
   } catch (NumberFormatException e) {
       // Skip invalid header value
   }
   ```

3. **资源清理**
   ```java
   try {
       filterChain.doFilter(request, response);
   } finally {
       TenantContext.clear(); // 防止 ThreadLocal 内存泄漏
   }
   ```

## 凭证管理架构

### 设计目标

将用户认证凭证从 User 表的 `password_hash` 字段抽象为独立的 `t_user_credential` 表，实现：
- 支持多种凭证类型（密码、证书）统一管理
- Admin 模块和 Auth 模块职责分离
- 凭证生命周期管理（创建、查询、更新、吊销）
- 多凭证支持（用户可拥有多个密码或证书凭证）

### 数据库设计

**表结构：** `t_user_credential`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT (PK) | 主键 |
| user_id | BIGINT (FK) | 关联用户 |
| credential_type | VARCHAR(30) | 凭证类型：PASSWORD, CERTIFICATE |
| credential_value | TEXT | 凭证值（密码哈希或证书PEM数据） |
| algorithm | VARCHAR(30) | 加密算法：BCRYPT |
| is_primary | BOOLEAN | 是否主凭证 |
| expires_at | TIMESTAMP | 过期时间（可选） |
| last_used_at | TIMESTAMP | 最后使用时间 |
| status | VARCHAR(20) | 状态：ACTIVE, EXPIRED, REVOKED |
| created_at | TIMESTAMP | 创建时间 |
| updated_at | TIMESTAMP | 更新时间 |

**约束和索引：**
- 外键：`user_id` REFERENCES `t_user(id)` ON DELETE CASCADE
- 唯一索引：`uk_user_type_primary` ON `(user_id, credential_type)` WHERE `is_primary = TRUE`
- 普通索引：`idx_user_credential_user_id`, `idx_user_credential_type`
- 检查约束：`credential_type IN ('PASSWORD', 'CERTIFICATE')`, `status IN ('ACTIVE', 'EXPIRED', 'REVOKED')`

### 模块职责分离

**Admin 模块（凭证管理）：**
- 完整的凭证 CRUD 操作
- 凭证状态管理（激活、过期、吊销）
- 密码修改和重置
- 凭证过期策略管理
- 富领域模型：`UserCredential` 实体包含工厂方法和行为方法

**Auth 模块（凭证验证）：**
- 只读凭证查询（用于认证流程）
- 更新凭证最后使用时间
- 贫血模型：`User` 实体仅包含字段，无行为方法
- 认证策略通过只读仓储获取凭证进行验证

### 凭证类型枚举

**CredentialType：**
- `PASSWORD` - 本地密码认证
- `CERTIFICATE` - 数字证书认证

**CredentialStatus：**
- `ACTIVE` - 激活状态（可用于认证）
- `EXPIRED` - 已过期（不可用于认证）
- `REVOKED` - 已吊销（不可用于认证）

### 核心实体方法

**UserCredential 工厂方法：**
```java
// 创建密码凭证
UserCredential.createPassword(userId, rawPassword, encoder)

// 创建证书凭证
UserCredential.createCertificate(userId, pemData)
```

**UserCredential 行为方法：**
```java
// 吊销凭证
credential.revoke()

// 标记为已过期
credential.expire()

// 更新最后使用时间
credential.updateLastUsed()
```

### 凭证管理 API

**Admin 模块端点：**
```
POST   /api/admin/users/{userId}/credentials           - 创建凭证
GET    /api/admin/users/{userId}/credentials           - 查询凭证列表
GET    /api/admin/users/{userId}/credentials/{id}      - 查询凭证详情
PUT    /api/admin/users/{userId}/credentials/{id}      - 更新凭证
DELETE /api/admin/users/{userId}/credentials/{id}      - 删除凭证
POST   /api/admin/users/{userId}/credentials/change-password - 修改密码
```

### 业务规则

1. **防锁定规则：** 禁止删除最后一个活跃的密码凭证
2. **主凭证唯一：** 每个用户的每种凭证类型只能有一个主凭证
3. **状态约束：** 只有 ACTIVE 状态的凭证才能被吊销
4. **密码编码：** 密码必须使用 BCrypt 编码后存储
5. **级联删除：** 删除用户时自动删除其所有凭证

### 认证流程集成

**PasswordAuthenticationStrategy 流程：**
```
1. 根据 username 查找 User
2. 从 t_user_credential 表获取主密码凭证
   credentialRepository.findPrimaryCredential(userId, PASSWORD)
3. 使用 BCrypt 验证密码
   passwordEncoder.matches(inputPassword, credentialValue)
4. 验证成功后更新 last_used_at
5. 返回 User 对象
```

### 第三方凭证说明

**LDAP/AD 凭证：** 
- LDAP 凭证**不存储**在本地数据库中
- 每次认证时直接向 LDAP/AD 服务器验证
- 仅在认证流程中使用，不持久化到 t_user_credential 表

**OAuth2 社交登录凭证：**
- 社交登录凭证由第三方提供商管理
- 本地仅存储用户关联信息（provider + provider_user_id）
- 不存储 OAuth2 access_token 或 refresh_token 到凭证表

### 1. OIDC/OAuth2 (Spring Authorization Server)

Spring Authorization Server 已经内置了完整的 OAuth2/OIDC 协议支持。

#### 授权码模式 (Authorization Code Grant)

**端点：** `/oauth2/authorize` → `/oauth2/token`

**流程：**
```
客户端 → /oauth2/authorize → 用户登录（调用认证层） → 授权码 → /oauth2/token → Access Token
```

**特点：**
- ✅ 最安全的 OAuth2 模式
- ✅ 支持 PKCE（公共客户端必需）
- ✅ 支持 OIDC（OpenID Connect）
- ✅ 用户通过浏览器完成认证
- ✅ 客户端不接触用户密码

**在统一框架中的位置：**
- 用户登录阶段 → 调用 AuthenticationStrategy（密码/验证码/社交等）
- 认证成功 → UnifiedAuthenticationSuccessHandler
- 恢复 SavedRequest → 继续授权流程
- 生成授权码 → Spring Authorization Server
- 换取 Token → Spring Authorization Server

**实现文件：**
- `AuthorizationServerConfig.java` - 授权服务器配置
- `RegisteredClientRepositoryAdapter.java` - 客户端注册
- `UnifiedAuthenticationSuccessHandler.java` - 认证成功后处理

##### PKCE（Proof Key for Code Exchange）

PKCE 是授权码模式的**增强机制**，用于防止授权码劫持攻击。它不是独立的授权模式。

**适用场景：** 公共客户端（SPA、移动端）无法安全存储 client_secret，必须使用 PKCE。

**流程差异：**
```
标准授权码:  /oauth2/authorize → code → /oauth2/token (client_secret) → Token
PKCE 流程:  /oauth2/authorize (code_challenge) → code → /oauth2/token (code_verifier) → Token
```

**关键参数：**
- `code_challenge`：授权请求时发送（code_verifier 的 SHA256 哈希，Base64Url 编码）
- `code_challenge_method=S256`：指定哈希算法
- `code_verifier`：换取 Token 时发送原始随机字符串

**在统一框架中的位置：**
- PKCE 验证由 Spring Authorization Server 在 `/oauth2/token` 端点自动处理
- 无需额外的认证策略或管道处理

#### SSO 主动推送授权码 (Proactive Code Push)

**场景描述：** 传统 OAuth2 授权码流程是"被动"的——客户端先发起 `/oauth2/authorize` 请求，SSO 响应。
某些场景下，需要 SSO 平台**主动**生成 Authorization Code 并重定向到应用，而不等待客户端先发起请求。

**典型场景：**
- **门户推送登录**：企业门户首页，点击"进入某应用"，自动完成 SSO 登录
- **应用间跳转**：从应用 A 跳转到应用 B，携带 SSO 认证状态
- **管理员代登录**：管理员帮用户进入某应用进行问题排查

**端点：** 自定义 `/api/sso/push/{clientId}`

**流程：**
```
用户在 SSO 平台（已登录）
  │
  │  点击"进入应用 B"
  │ ──────────────────────>│  POST /api/sso/push/app-b
  │                        │
  │                        │  1. 校验 clientId 是否存在
  │                        │  2. 获取 redirect_uri、scope 等配置
  │                        │  3. 构造内部授权请求
  │                        │  4. 框架生成 Authorization Code
  │                        │  5. 302 重定向到 redirect_uri?code=xxx
  │                        │
  │  <─────────────────────│
  │  302 → redirect_uri?code=AUTH_CODE&state=xxx
  │
  │  6. 应用 B 用 code 换 token（标准流程）
  │ ──────────────────────>│  POST /oauth2/token
  │                        │  grant_type=authorization_code
  │                        │  code=AUTH_CODE
  │                        │
  │  <─────────────────────│  {access_token, id_token}
```

**实现方案：**

推荐通过**服务端模拟授权请求**实现，不修改 Spring AS 内部逻辑：

```java
@RestController
@RequestMapping("/api/sso")
@RequiredArgsConstructor
public class SsoProactiveAuthController {
    
    private final RegisteredClientRepository clientRepository;
    private final SecurityContextRepository securityContextRepository;
    private final AuthorizationService authorizationService;
    private final OAuth2AuthorizationRequestResolver authorizationRequestResolver;
    
    /**
     * SSO 主动推送授权码
     * 
     * 原理：在服务器端模拟一次授权请求，利用 Spring AS 的标准流程生成 Code，
     *      然后手动提取 Code 并重定向到应用的 redirect_uri。
     */
    @GetMapping("/push/{clientId}")
    public void pushAuthCode(
            @PathVariable String clientId,
            @RequestParam(required = false) String state,
            @RequestParam(required = false) String nonce,
            HttpServletRequest request,
            HttpServletResponse response) throws IOException {
        
        // 1. 检查用户是否已登录
        Authentication authentication = SecurityContextHolder.getContext().getAuthentication();
        if (authentication == null || !authentication.isAuthenticated()) {
            // 未登录：记录当前意图，登录完成后继续推送
            // 可以通过 SavedRequest 机制实现
            response.sendRedirect("/login?redirect=/api/sso/push/" + clientId);
            return;
        }
        
        // 2. 查找客户端配置
        RegisteredClient client = clientRepository.findByClientId(clientId);
        if (client == null) {
            response.sendError(HttpServletResponse.SC_BAD_REQUEST, "Invalid client_id");
            return;
        }
        
        // 3. 获取默认的 redirect_uri（取第一个）
        String redirectUri = client.getRedirectUris().iterator().next();
        
        // 4. 构造模拟的授权请求 URL
        String authUrl = "/oauth2/authorize?"
            + "response_type=code"
            + "&client_id=" + clientId
            + "&redirect_uri=" + URLEncoder.encode(redirectUri, "UTF-8")
            + "&scope=" + URLEncoder.encode(String.join(" ", client.getScopes()), "UTF-8")
            + (state != null ? "&state=" + state : "")
            + (nonce != null ? "&nonce=" + nonce : "");
        
        // 5. 服务端内部转发到 /oauth2/authorize
        //    Spring AS 会检测到用户已登录，直接生成 Code 并重定向
        request.getRequestDispatcher(authUrl).forward(request, response);
    }
}
```

**安全注意事项：**

1. **用户必须已登录**：如果用户未登录，会跳转到登录页，登录完成后自动继续推送流程
2. **redirect_uri 校验**：由 Spring AS 自动校验，确保与客户端注册时一致
3. **PKCE 兼容**：如果客户端要求 PKCE，应用端在换取 Token 时仍需提供 code_verifier
   - 推荐方案：推送前通过前端 JavaScript 生成 code_challenge/code_verifier 对
   - 或者：为内部推送场景设置专门的客户端配置，不强制 PKCE
4. **防 CSRF**：state 参数应始终传递，应用端校验 state 一致性
5. **频率限制**：对推送接口增加速率限制，防止滥用

**与传统授权码模式的对比：**

| 维度 | 传统授权码模式 | SSO 主动推送 |
|------|--------------|-------------|
| 发起方 | 客户端应用 | SSO 平台 |
| 用户感知 | 浏览器重定向 | 浏览器重定向（相同） |
| 是否需用户登录 | 是 | 是（否则跳登录页） |
| Code 生成方式 | 标准 `/oauth2/authorize` | 内部转发到同一端点 |
| 安全性 | 高 | 等同（复用同一安全机制） |
| PKCE 支持 | 完全支持 | 需额外处理 |

```java
@Component
@RequiredArgsConstructor
public class CasServerAdapter {
    
    private final AuthenticationDispatcher dispatcher;
    private final CasTicketService ticketService;
    
    @PostMapping("/cas/login")
    public ResponseEntity<?> handleCasLogin(
            @RequestParam String username,
            @RequestParam String password,
            @RequestParam String service,
            HttpServletRequest request) {
        
        // 1. 使用密码认证
        PasswordCredentials credentials = new PasswordCredentials(username, password);
        AuthenticationResult result = dispatcher.authenticate(credentials);
        
        // 2. 生成 Service Ticket
        String ticket = ticketService.createServiceTicket(result, service);
        
        // 3. 重定向到 service?ticket=xxx
        return ResponseEntity.status(302)
            .header(HttpHeaders.LOCATION, service + "?ticket=" + ticket)
            .build();
    }
    
    @GetMapping("/cas/serviceTicket")
    public ResponseEntity<?> validateServiceTicket(
            @RequestParam String ticket) {
        
        // 验证 Ticket 并返回用户信息
        CasValidationResponse response = ticketService.validate(ticket);
        return ResponseEntity.ok(response);
    }
}
```

## 安全考虑

### 身份认证层安全

1. **密码安全**
   - BCrypt 加密存储（单向，不可逆）
   - 密码凭证存储在独立的 `t_user_credential` 表，与 User 表分离
   - Admin 模块统一管理凭证生命周期（创建、查询、更新、吊销）
   - Auth 模块仅通过只读仓储访问凭证进行认证
   - 速率限制，防止暴力破解
   - 账户锁定机制（多次失败后锁定）
   - 审计日志记录所有认证尝试
   - 禁止删除最后一个活跃的密码凭证（防止用户被锁定）

2. **验证码安全**
   - 验证码有效期限制（通常 5 分钟）
   - 一次性使用，验证后立即失效
   - 发送频率限制，防止短信轰炸

3. **社交登录安全**
   - 验证 state 参数，防止 CSRF
   - 校验 provider 返回的用户信息签名
   - 支持账号绑定和解绑

4. **LDAP 安全**
   - LDAP 连接使用 LDAPS（加密传输）
   - 密码不缓存，每次请求验证
   - 域账号锁定策略遵循 AD 域配置

### 协议接入层安全

#### OIDC/OAuth2 安全

- RSA 密钥对安全存储（DEV 使用密钥文件，PROD 通过 K8s Secret/Vault 注入）
- 强制 Public Client 使用 PKCE（Proof Key for Code Exchange）
- Token 生命周期合理控制（Access Token 默认 1 小时，Refresh Token 默认 24 小时）
- JWT 签名使用 RS256 非对称加密
- 防止 Token 重放攻击
- 授权同意页面必须经过用户确认

#### SAML 安全要点

1. **签名验证** - 验证 SAML 响应的数字签名
2. **时效性检查** - 防止重放攻击（NotBefore / NotOnOrAfter）
3. **Audience 验证** - 确保响应是发给本服务的
4. **HTTPS 强制** - 所有通信必须加密

#### CAS 安全要点

1. **Ticket 一次性** - Service Ticket 验证后立即失效
2. **HTTPS 强制** - Ticket 传输必须加密
3. **Service 白名单** - 只允许注册过的服务请求 Ticket

### 场景 6：SSO 主动推送授权码，门户用户一键进入应用

**前提：** 用户已在 SSO 平台登录，门户首页展示用户可访问的应用列表。

**Step 1: 用户点击"进入应用 B"**
```
用户在门户首页点击应用 B 的"进入"按钮
  → GET /api/sso/push/app-b?state=random-state
```

**Step 2: SSO 内部转发到授权端点**
```
SSO 检测到用户已有活跃会话
  → 内部转发到 /oauth2/authorize?client_id=app-b&redirect_uri=...
  → Spring AS 生成 Authorization Code
  → 302 重定向到应用 B
```

**Step 3: 应用 B 收到授权码**
```
重定向到: https://app-b.example.com/callback?code=AUTH_CODE&state=random-state
```

**Step 4: 应用 B 用 code 换 Token（标准流程）**
```bash
curl -X POST https://sso.example.com/oauth2/token \
  -d "grant_type=authorization_code" \
  -d "code=AUTH_CODE" \
  -d "redirect_uri=https://app-b.example.com/callback" \
  -d "client_id=app-b" \
  -d "client_secret=app-b-secret"
```

**响应：**
```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "dGhpcyBpcyBhIHJlZnJlc2ggdG9rZW4",
  "scope": "openid profile",
  "id_token": "eyJhbGciOiJSUzI1NiIs..."
}
```

**关键点：**
- 用户无需再次输入密码（SSO 会话有效）
- 应用 B 无需改造，完全兼容标准 OAuth2 流程
- Code 的生成、校验、换取 Token 全部复用 Spring AS 标准机制

## 扩展指南

### 添加新的认证方式（身份认证层）

以添加"生物识别认证"为例：

#### Step 1: 添加凭证类型

```java
// AuthenticationCredentials.java
record BiometricCredentials(String userId, String biometricToken, String deviceType) 
    implements AuthenticationCredentials {
    public BiometricCredentials {
        if (userId == null || userId.isBlank())
            throw new IllegalArgumentException("User ID is required");
        if (biometricToken == null || biometricToken.isBlank())
            throw new IllegalArgumentException("Biometric token is required");
    }
}
```

#### Step 2: 实现认证策略

```java
@Service
@RequiredArgsConstructor
public class BiometricAuthenticationStrategy implements AuthenticationStrategy {
    
    private final BiometricValidator biometricValidator;
    private final UserRepository userRepository;
    
    @Override
    public AuthenticationMethod getMethod() {
        return AuthenticationMethod.BIOMETRIC;
    }
    
    @Override
    public boolean supports(AuthenticationCredentials credentials) {
        return credentials instanceof AuthenticationCredentials.BiometricCredentials;
    }
    
    @Override
    public AuthenticationResult authenticate(AuthenticationCredentials credentials) {
        BiometricCredentials bc = (BiometricCredentials) credentials;
        
        // 1. 验证生物识别 token
        boolean valid = biometricValidator.validate(bc.biometricToken(), bc.deviceType());
        if (!valid) {
            throw new AuthenticationException("Invalid biometric token");
        }
        
        // 2. 查找用户
        return userRepository.findById(bc.userId())
            .map(user -> AuthenticationResult.success(user))
            .orElseThrow(() -> new AuthenticationException("User not found"));
    }
}
```

#### Step 3: 添加 REST 端点

```java
@RestController
@RequestMapping("/api/auth")
@RequiredArgsConstructor
public class BiometricAuthController {
    
    private final AuthenticationDispatcher dispatcher;
    private final UserApplicationService userService;
    
    @PostMapping("/biometric")
    public ResponseEntity<?> authenticateBiometric(
            @RequestBody BiometricLoginRequest request,
            HttpServletRequest httpRequest) {
        
        BiometricCredentials credentials = new BiometricCredentials(
            request.userId(), request.biometricToken(), request.deviceType());
        
        AuthenticationResult result = dispatcher.authenticate(credentials);
        userService.completeAuthentication(result, AuthenticationMethod.BIOMETRIC, httpRequest);
        
        return ResponseEntity.ok(buildTokenResponse(result));
    }
}
```

### 添加新的协议接入（协议接入层）

以添加"自定义 JWT API"为例：

#### Step 1: 实现协议适配器

```java
@Component
@RequiredArgsConstructor
public class JwtApiAdapter {
    
    private final AuthenticationDispatcher dispatcher;
    private final UserApplicationService userService;
    private final JwtTokenService jwtService;
    
    /**
     * 自定义 JWT API 端点
     */
    @PostMapping("/api/auth/jwt-login")
    public ResponseEntity<?> handleJwtLogin(
            @RequestBody JwtLoginRequest request,
            HttpServletRequest httpRequest) {
        
        // 1. 调用认证层（使用密码认证）
        PasswordCredentials credentials = new PasswordCredentials(
            request.username(), request.password());
        AuthenticationResult result = dispatcher.authenticate(credentials);
        
        // 2. 运行后处理管道
        userService.completeAuthentication(result, AuthenticationMethod.PASSWORD, httpRequest);
        
        // 3. 生成自定义 JWT（不走 OIDC 流程）
        String token = jwtService.createToken(result);
        
        return ResponseEntity.ok(Map.of(
            "access_token", token,
            "token_type", "Bearer",
            "expires_in", 3600
        ));
    }
}
```
